# 治理与变更流程

UHP 在 [HarnessRouter 仓库](https://github.com/HarnessRouter/harnessrouter)中维护，采用维护者主导、提案优先的模式。本文档定义其变更方式。

## 原则

1. **先文字，后代码。** 变更始于对问题的描述，而非 Pull Request。补丁是答案；提案必须先确立问题。
2. **三份产物同步推进。** 除非规范、参考实现和一致性测试套件在同一次变更中一并更新，否则变更不予合入。没有任何东西强制执行的规范条文只是一厢情愿。
3. **兼容性是一项特性。** 破坏合规客户端的变更需要新版本和迁移路径，而不是在变更日志里加一条说明。
4. **门槛是可运行的实现。** 提案不会因优雅而被接受。必须有东西能跑起来。

## 流程

### 1. 提案

以 GitHub Issue 形式提交 **UHP 增强提案（UEP）**，打上 `uep` 标签，内容包括：

- **问题** —— 开发者今天具体做不到什么。
- **提案** —— 变更内容，详细到足以被质疑。
- **兼容性** —— 什么会被破坏，以及针对当前版本编写的客户端会经历什么。
- **备选方案** —— 还考虑过什么，为什么更差。

文字即可。UEP 不需要补丁，补丁也不能替代上述内容。

### 2. 讨论

维护者在 10 个工作日内回复以下之一：**原则上接受**、**需要完善**、**拒绝并说明理由**。拒绝会连同理由一并记录，以免同一提案被从头重新争论。

### 3. 实现

被接受的 UEP 以单个 Pull Request 实现，包含全部三份产物：

- [ ] 规范章节已更新
- [ ] `schema/` 中的 OpenAPI + JSON Schema 已更新
- [ ] 参考实现已更新
- [ ] 新增一致性测试，变更前失败、变更后通过
- [ ] `CHANGELOG.md` 条目

缺少任何一项的 Pull Request 都不算就绪，代码再好也不行。

### 4. 发布

增量变更进入当前版本。破坏性变更按 [VERSIONING.md](VERSIONING.md) 累积为新的带日期版本，发布时附迁移说明。

## 角色

- **维护者** —— 拥有合并权限；负责三份产物之间的一致性，以及回复 UEP。
- **贡献者** —— 任何提交 UEP、Pull Request 或 Issue 的人。
- **实现者** —— 任何发布 UHP 服务端或客户端的人。在任何设计争论中，实现者的反馈优先于理论上的优雅。

## 被拒绝的字段不是待定字段

实现可以选择不携带某个字段。这个选择是一项**决定**，应当作为决定记录下来——而不是留在一份读起来像"还没人做"的清单上。

这一区分很重要，因为从外部看两者一模一样。实现打算以后支持的字段，和决定永不支持的字段，表现方式相同：请求要了但没得到。如果不加说明，后者会悄悄变成前者，一个本已解决的问题会被每个新读者、每个新实现者和每次 Issue 分类重新打开。

因此：

- **说清是哪一种。** 被拒绝的字段就此关闭。说明原因，一次，写在持久的地方，别再把它当作待办项。
- **拒绝只关乎实现，绝不关乎校验。** [Tasks §1.1](versions/2026-08-11/tasks.md#11-request-fields) 要求忽略而非拒绝，所以被拒绝的字段仍会被接受，携带它的请求仍会执行。
- **告知调用方。** 被丢弃的字段会在 `metadata.ignored_fields` 中列出。被静默忽略的字段与被采纳的字段无法区分，调用方无从知道自己得到的是哪种。这与 [Tasks §1.3](versions/2026-08-11/tasks.md#13-model-selection-and-substitution) 中报告模型替换是同一原则。

这也适用于规范本身，`tools` 和 `include` 就是现成的例子：与其让它们规范不足、任由每个实现者猜测，不如在 [Tasks §1.4](versions/2026-08-11/tasks.md#14-reserved-fields-tools-and-include) 中声明为保留并忽略，并写明原因。

这一框架和措辞来自 @aenawi 在 [#42](https://github.com/HarnessRouter/harnessrouter/issues/42) 中的贡献，出自一个独立 UHP 实现的 ADR-0007。

## 问题报告

- **规范缺陷** —— 歧义、无法实现的规则、规范与测试套件不一致：提交打上 `spec-bug` 标签的 Issue。这些按缺陷处理。
- **参考实现中的缺陷** —— GitHub Issues。
- **安全漏洞** —— 私下披露，不要公开提交 Issue。参见仓库的安全政策。

## 一致性声明

"UHP <版本> 合规（类别）"意味着一致性测试套件在该类别下针对提供该版本的服务端全部通过。声明时应当同时发布报告。没有认证机构，没有费用，也没有标志计划——测试套件就是权威，它就在本仓库中，任何人都可以拿它去测任何人的服务端。

网站确实会发布徽章，但它不是一项计划：它只是报告的呈现。当 `conformance-measure` 工作流针对某个实现运行完毕，且其报告已落入 `conformance/reports/`，网站会生成徽章，标明完全通过的最高类别和所服务的版本，该实现的列表页会显示它。无需申请，无人审批；报告就是全部证据，若重新测量在徽章标明的类别上失败，下次构建时徽章即被移除。

## 命名与一致性

本标准的正式名称是 Unified Harness Protocol（UHP）。其网站为 https://unifiedharnessprotocol.org。

Apache-2.0 按其条款授予代码和规范的权利。它不授予协议名称的权利。"Unified Harness Protocol" 和 "UHP" 是 HarnessRouter 的商标。

实现只有在通过 [`conformance/`](conformance/) 中的一致性测试套件后，才能自称"UHP 兼容"或"实现 UHP"。通过该套件是本项目对合规的定义。不合规的实现、部分实现和修改过的 Fork 不得以暗示兼容的方式使用该名称。如实说明产品"可与 UHP 配合"或"可连接 UHP"是可以的。

商标与兼容性声明相关问题可发送至 contact@harnessrouter.ai。
