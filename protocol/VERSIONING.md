# 版本管理与兼容性

## 方案

UHP 版本采用日期格式——`YYYY-MM-DD`，即版本发布当天。`2026-10-04` 是当前版本；`2026-09-28`、`2026-09-12` 和 `2026-08-11` 仍在发布并提供服务。

选择日期而非语义化版本是刻意的。SemVer 的承诺是：主版本号变更意味着"预期会有破坏性变更"，次版本号变更意味着"安全"——这个承诺的好坏完全取决于分配版本号者的自律程度，而实践中它经常被打破。日期不承诺任何它无法兑现的东西。它只说明版本何时发布，可以排序，并让实现的新旧程度一目了然。

## 同一版本内可以变更的内容

已发布的版本**在结构上不可变**。在同一版本内，服务器可以：

- 添加可选的请求字段；
- 向响应对象添加字段；
- 添加新的事件类型；
- 添加带厂商前缀的新错误码；
- 放宽约束（接受之前拒绝的输入）。

在同一版本内，服务器不得：

- 删除或重命名字段；
- 更改字段的类型或含义；
- 添加必填的请求字段；
- 删除事件类型或错误码；
- 收紧约束（拒绝之前接受的输入）。

第二类中的任何变更都需要新版本。

## 客户端规则

符合规范的客户端必须：

1. **忽略未知字段。** 不警告，不报错——直接忽略。
2. **忽略未知事件类型。** 跳过并继续读取流。
3. **忽略未知的输出项类型。** 只渲染能理解的部分。
4. **将未知错误码按其 `type` 处理。** 无法识别的 `code` 若带有 `type: "server_error"`，仍可重试。

遵循这四条规则的客户端，在同一版本内的所有增量变更中都能持续工作——这正是把它们写下来的全部意义。

## 服务器规则

服务器必须：

1. 在 `UHP-Version` 响应头中报告所服务的版本。
2. 对不支持的被请求版本返回 `unsupported_protocol_version`，而不是提供另一个版本。
3. 至少同时支持一个完整版本，并且在新版本发布后，应至少支持上一个版本六个月。当较新版本是增量变更时——如 `2026-10-04` 之于 `2026-09-28`、后者之于 `2026-09-12`、再后者之于 `2026-08-11`——所有版本由同一代码路径提供服务：相同的对象响应任一请求，客户端唯一能看到的差异是响应头中回显的版本号。

## 弃用

字段或端点的弃用流程为：

1. 在规范和 OpenAPI 文档中标记为已弃用，并注明原因和替代方案；
2. 至少保持其可用两个已发布版本；
3. 最早在公告后的第二个版本中移除。

任何内容都不会在没有可用替代方案的情况下被移除。

## 当前版本的已知妥协

记录于此，是因为一个隐藏自身粗糙边缘的规范，在光滑之处也不可信。

- **字段命名风格混用。** 任务接口使用 `snake_case`；harness 对象使用 `camelCase`。两者在已发布的客户端中都是关键依赖。未来的主版本应统一它们。
- **会话删除也位于 `/v1/traces/{id}`。** 该路径早于会话术语体系。协议现在命名 `DELETE /v1/sessions/{id}`，并保留旧路径作为别名而非重命名，因为重命名会为了表面上的收益而破坏现有客户端。未来的主版本可通过上述流程淘汰旧路径。
- **Harness 写入会拒绝无法存储的内容。** 自 2026-10-10 起，两个维护中的服务器都会拒绝携带 harness 不具备的字段的 harness 创建或更新请求（`422`，并指明该字段及其最接近的已有字段），或拒绝其 base 不运行的 `default_model`（`422`，`model_not_available`）。这两项都是上述规则保留给新版本的收紧。它们是在 `2026-10-04` 内做出的，因为它们所拒绝的输入此前会在 `200` 背后被存储为空，而运行在无 base 支持的模型上的 harness 会拒绝分配给它的每个任务；客户端，尤其是驱动 API 的 agent，无从得知原因。harness 对象返回但无法写入的内容（`id`、`object`、`createdAt` 以及服务器自身的只读字段）仍会被接受并忽略，因此读取 harness 再发回可以正常保存。下一个版本在 [Harnesses §5](versions/2026-10-04/harnesses.md#5-managing-harnesses) 中明确陈述了这两条规则。
