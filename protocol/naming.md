# 统一 Harness 协议的命名

**HarnessRouter 如何命名 harness 运行层、过程中权衡的九个名称，以及为什么 Unified 让契约保持完整。**

## 简短回答

统一 Harness 协议（UHP）定义了一份共享契约，用于通过单一接口运行 agent harness。agent harness 是把模型变成可工作 agent 的运行时：它规划、调用工具、反复迭代直到任务完成。HarnessRouter 命名了这一层——harness 运行层，并将其开创为一个类别；UHP 定义了它的公共边界。它是一份公开的、带版本的契约，让 harness 的运行变得可移植、可检查、可独立测试，因此调用方通过一个接口就能触达符合规范的服务器所暴露的任何 harness，无需改动集成。

"Unified"（统一）是关键的那个词，它是对完整性的主张。运行一个 harness 不是一次调用，而是一整个生命周期：会话、流式传输、文件、产物、取消、失败处理。我们权衡过的其他名称，要么只覆盖了这个生命周期的一部分，要么只抓住了我们希望契约保留的某个属性。UHP 是唯一一份把这一切都囊括其中的契约，因此应用通过单一接口与 harness 对话，而不必拼接多个接口。本页就是这一决策的记录：九个名称，权衡之后归结为一个协议。

## 问题：一个 harness，多个界面

当你着手标准化 harness 运行层时，会发现根本没有单一的接缝可供标准化。通过契约运行 harness，意味着同时覆盖多个界面：如何打开和恢复会话，进度和事件如何流式返回（包括 harness 工作时发起的工具调用），文件如何输入、产物如何输出，工作如何被取消，失败如何被报告。除了这些界面之外，还有两个你希望整份契约无论如何都保持的品质：保持厂商中立，保持开放。

每个界面天然地暗示了各自的协议名称。顺着这种直觉走，在任何一个实现发布之前，这个领域就会碎裂成一堆相邻缩写的家族，每个都有自己的 Schema 和治理方式。这件事关乎整个行业：没有统一契约，每个想做 agent 的产品都要重建同样的集成，一个 harness 一套；每个 harness 构建者也要反向重建同样的产品接缝。所以真正的问题从来不是缩写，而是架构问题，它决定了整个领域如何看待这一层：这些是彼此独立的协议，还是一份契约的各个部分？我们选择了一份契约。

## 九个名称，一个协议（UHP）

我们权衡了九个名称，结论是架构性的：它们没有一个命名的是独立协议。每一个都归结为 UHP，或是契约的一个界面、一个属性、一项能力，或是你在其上构建的一种模式。下表列出七个，六行共七个名称，因为有两个共享同一角色和同一缩写。最后两个是名称本身的候选，二者的取舍见表格之后。

| 名称 | 缩写 | 类别 | 它抓住了什么 |
| --- | --- | --- | --- |
| Application Harness Protocol | AHP | UHP 的界面 | 集成：产品如何嵌入并驱动 harness。 |
| Harness Application Protocol | HAP | UHP 的界面 | 同一条集成接缝，从 harness 一侧命名。 |
| Harness Communication Protocol 与 Harness Client Protocol | HCP | UHP 的界面 | 客户端与 harness 的对话：消息传输线，以及消费它的客户端或 SDK。 |
| Meta Harness Protocol | MHP | UHP 的能力 | 在一份契约下运行多个 harness，使其运行结果可直接比较；调用方施加自己的指标。重写单个 harness 的优化器，只是这份契约的又一个客户端。 |
| Open Harness Protocol | OHP | UHP 的属性 | 开放性：公开、无锁定、规范化的规格，是一种价值而非请求路径。 |
| Harness-to-Harness | H2H | 一种 UHP 模式 | harness 委托给 harness，由重复的 UHP 调用构建：harness 通过一个运行另一个 harness 的工具来委托，或由调用方直接编排多次运行。 |

把这张表当作地图来读。AHP 和 HAP 是同一条集成接缝的两面。两个 HCP 名称是同一场对话的两个深度描述——它传输所经的线路，以及消费它的客户端；恰如其分地，它们落在了同一个缩写上。OHP 不是界面，而是我们希望契约保留的一种价值。

"Meta-harness"分两种理解。运行多个 harness 并比较它们，是统一契约承载的一项能力：因为每次运行都经过同一份契约，运行结果可直接比较，调用方施加对自己有意义的指标。搜索、调优、挑选优胜者，按设计属于调用方。改进单个 harness 则是另一回事：一个外层循环，依据 harness 自身的执行记录重写它，即 [Stanford 的 Meta-Harness 工作](https://arxiv.org/abs/2603.28052)所描述的形式，一篇 2026 年的 arXiv 预印本。这类优化器是运行结果的消费者，不是协议；它赖以运行的，正是 UHP 产出并使之可比较的那些运行。无论哪种理解，meta-harness 都是 UHP 的一项能力：运行并比较多个 harness 是这一份契约使之成为可能的事，而改进单个 harness 则建立在它产出的运行结果之上。

H2H 是同一个故事再往外一步。harness 会规划并调用工具，所以给它一个通过同一份契约运行另一个 harness 的工具，委托和扇出就由重复的 UHP 调用构建而成。一个会话从头到尾保持一个配置好的 harness，因此协调逻辑位于调用方；这不是对该模式的限制，而是使它可组合的设计，因为每次调用底下的契约始终一致。这也是 UHP 与 Agent2Agent（A2A）互补而非竞争的原因。A2A 是 agent 之间直接发现并互发消息的对等协议；UHP 是调用方用来运行它所协调的每个 harness 的契约。这些名称没有一个错了。每一个都归结为 UHP，只是从某一面看过去。

## 决策：为什么 Unified 赢得了 UHP 这几个字母

最后两个名称从未进入表格，因为二者都是名称本身的候选，而非名称所覆盖之物的候选。两个都是形容词，且都想要同样的三个字母：Universal Harness Protocol 和 Unified Harness Protocol。

Universal 是对覆盖范围的主张：它说该协议适用于所有厂商。这是值得坚持的目标，但覆盖范围是协议赢得的属性，不是它的形态，而且它留下了一个真正的问题：覆盖什么？

Unified 回答了这个问题。它说整个运行契约是一个协议，而非一堆散落的协议。Universal 描述协议触及什么；Unified 描述协议是什么。所以 UHP 取 Unified，而普适性作为这一份契约所交付的东西之一，存在于它内部。

## 设计上开放

这一层的契约，只有在无人能独占时才值得统一。UHP 在构造上就是开放的，因此开放性无需成为名称：规范公开，任何人都可实现，一致性测试套件在本地运行，将实现评定为不同的一致性等级。一致性适用于暴露 harness 的服务器，因此互操作性是可独立验证的属性，而非一句承诺。它是一份带版本的 HTTP 契约，用 OpenAPI 3.1 和 JSON Schema 2020-12 定义，发布在 unifiedharnessprotocol.org，并作为一份契约成长：UHP 协商版本并通告能力，因此客户端能确切发现某个 harness 支持什么，而不必每走一步就冒出一个新协议。

## UHP 按设计唯一不碰的东西

"Unified"是对运行 harness 之契约的主张，它止于一条刻意划下的线：harness 自身的推理——它如何规划、决策、迭代直至得出结果。正是这种判断力让一个 harness 值得被选中而非另一个，所以 UHP 标准化的是围绕 harness 的契约，而不是 harness 的思考方式。

这条线之前的一切都通过一个接口运行，且在 harness 两侧都如此。一侧，UHP 统一了 harness 如何接入产品：产品集成一次，就能以同样方式驱动符合规范的服务器所暴露的任何 harness。另一侧，它统一了能力如何接入 harness：工具和技能（无论由 MCP 服务器提供，还是打包在 agent 插件中）通过同一份配置挂载，因此无论底下运行哪个 harness，接入一项能力的方式都完全相同。

围绕 harness 的每一条集成接缝都经由 UHP，这正是统一接口的全部意义：每条接缝一份契约，无论背后是哪个 harness。

而且这份契约是为了承载生态而非与之竞争：MCP 标准化能力如何暴露，Agent Plugins 标准化技能和 MCP 服务器定义如何打包，UHP 把二者纳入同一份配置，让这个领域的开放标准在一个接口中汇合，而不是碎裂成许多个。

## 参考实现

HarnessRouter 是全球首个面向 agent harness 的统一接口。

统一接口就是完整的运行契约：会话、流式传输、文件、产物、取消、失败处理，通过一个 API 触达。UHP 是 HarnessRouter 开创并主导的开放标准，其开源社区版以 Apache 2.0 许可发布，附带任何人都能运行的参考实现：一个符合规范的服务器，持有针对测试套件检查（目前 52 项）的 Full 级报告。

这就是"Unified"最终的含义：不是每个 harness 都相同，而是一份契约以开放的方式运行符合规范的服务器所暴露的每个 harness。当一个类别能在一条无人需要重新发明的边界之上，让产品和 harness 各自独立演进时，它才变得持久。HarnessRouter 命名了这个类别并划出了它的边界；UHP 是生态可以据以构建的公共契约。
