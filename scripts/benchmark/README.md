# 基准测试套件

支持矩阵证明的是测试框架*能用*。本套件衡量的是框架 × 模型配置把同样的活干得有多好：使用带确定性评分的公开任务套件，通过实例自身的 API 运行，每个会话一个任务，每个数字都取自运行器已经存储的轮次记录。下面的规则决定一行结果；`test_run.py` 把它们固定下来。

## 衡量什么

对每个指定的框架和模型，包中的每个任务都在全新会话中运行：包把任务的文件和指令作为第一轮暂存，该轮运行，它产出的文件从会话中取回，由套件自己的评分器判定。一条记录包含判定结果（`resolved`、[0, 1] 区间内的 `reward`、评分器的理由）、墙钟时间、工具调用及工具名、其中失败的调用数（CLI 标记了结果，或 shell 退出码非零或抛出异常——从存储的 trace 读取）、新输入 / 缓存 / 输出 token、轮次记录标注的连接和实际服务的模型，以及文件。表格按行汇总墙钟时间和工具调用，并把失败调用以比率给出。

包位于 `packs/`，每个一个模块，绝不重新实现评分器：套件的数据和评分器留在本仓库之外，位于 `PACK_ROOT`，遵循套件自己的许可。

| 包 | 套件 | 评分 | 评分机器上需要 |
|---|---|---|---|
| `spreadsheetbench` | [SpreadsheetBench Verified](https://github.com/RUCKBReasoning/SpreadsheetBench)（400 道真实电子表格操作题，NeurIPS 2024 D&B） | 套件的 `evaluation.py`，在答案范围内逐单元格比对 | `openpyxl`；LibreOffice（`soffice`），以便带公式保存的工作簿有值可比。每次评分都用各自的 profile 打开引擎，这样并行 worker 不会互相拒绝对方的锁；引擎无法求值的工作簿按保存状态评分，其记录会注明"公式未求值"及原因 |

## 决定一行结果的规则

**1. 它在你指定的地方运行。** 把 `EXPECT_CONNECTION` 设为被测连接；轮次记录标出其他连接的运行是发现项，绝不是分数。矩阵规则 1，不变。

**2. 它运行了你要求的东西。** 实际服务的模型与请求的 id 不同即为发现项，由 `samemodel.py` 按矩阵的判定方式判定：聚合器的前缀或提供商的版本后缀是同一模型，另一个家族、编号或层级则不是。轮次记录不带实际服务模型的框架仍计分，该行注明有多少次运行无法检查规则 2。

**3. 它做了任务，而不是查答案。** 沙箱有互联网和文件系统。首次试点的第三个任务从套件的公开数据里取到了自己的标准答案，因为任务 id 就在文件名里；之后有两轮从提示词中的字段名认出了套件，花了半小时在整个文件系统里 grep 它的数据，并试图 `pip download` 它。所以包不命名任何东西——工作簿是 `input.xlsx`，答案是 `output.xlsx`，提示词是普通词语，不含套件的任何词汇——而工具调用发起了请求（web 工具；shell 或脚本中的 `curl`、`wget`、`git clone`、`urllib.request`、`requests`、`httpx`、`aiohttp`）或在机器上搜索任务（根目录在工作区之外的递归 `grep`、`rg` 或 `find`；以套件名下载的包）的运行是发现项，绝不是分数。安装包是沙箱的正常流量，不算；仅在代码中拼出的 URL（xlsx 的 XML 命名空间）也不算；工作区归 agent 搜索，`/tmp` 作为其暂存区也是；其他所有绝对路径都在外面，包括 `/app` 下产品自身的代码。工具按名字判断是否为网络使用：名字表明它要联网（web、fetch、browse、URL、internet、按名字的搜索引擎），而不是仅因为它会搜索：cline 的 `search_files` 和代码库搜索搜的是工作区，不是发现项。同时关闭框架的 web 工具，在框架或连接上：规则能抓住开关漏掉的——而在开关只是给模型下指令的框架上（cline、dsh），它确实抓到过一次，两百次运行中的一次，任务进行到十五分钟时该次运行未完成。发现项的会话留在实例上；其 trace 就是证据。

**4. Token 用同一口径。** 新输入、缓存输入和输出分开报告，绝不求和：缓存读取是同一提示词再次读取，不是新输入。运行器的约定是 `input_tokens` = 新输入（codex、gemini 以及自 #209 起的 cline 都折算到它），`output_tokens` = 整个生成，含思考（自 #216 起对 opencode，它把推理与文本分开保存）。来自早于任一版本的实例的列，报告的 cline 输入是毛值，或 opencode 输出仅为可见文本，应放在运行备注里，而不是表格里：在一个任务上，文本只占模型生成量的 41%，而该框架却以它并未挣得的倍数被读成四者中最便宜的。

**5. 不用裁判。** 评分需要模型意见的套件不是包。发现项和运行器错误列在表格下方，不计分。套件自己的评分器无法判定的任务——其标准答案通不过——从该行剔除并计入备注，不算在每个框架头上：前五十个中有两个这样的，一个表名里带逗号，评分器据此切分答案范围，另一个是整列范围，评分器从中读行号。

每个任务都有时间上限 `TASK_CAP_S`（默认 900 秒）：到上限仍在运行的轮次通过 API 取消，按现状评分，算失败，不算发现项——上限是任务的一部分。该行注明有多少次运行触及上限。

提供商在 agent 做任何事之前就拒绝的轮次（401/402/429/5xx、余额不足、限流）衡量的是账户，不是框架：记为运行器错误，下次启动时重跑，连续三次则中止运行，而不是用同一行填满表格。

## 运行它

```
export BASE=http://127.0.0.1:3000/api/harness HR_API_KEY=... PROVIDER=deepseek EXPECT_CONNECTION=integration:deepseek
export PACK=spreadsheetbench PACK_ROOT=/data/spreadsheetbench_verified_400   # dataset.json + spreadsheet/ + the suite's evaluation.py, open_spreadsheet.py
HARNESSES=opencode=chrn_...,pi=chrn_...,cline=chrn_...,dsh=chrn_... MODELS=deepseek-v4.1-flash TASKS=first:50 \
  RESULTS=results-deepseek.json LOG=log-deepseek.txt WORKERS=2 python3 run.py
python3 render.py results-deepseek.json --note "self-hosted CE 0.18.4, 2026-09-19" > ../../docs/benchmark.md
```

`HARNESSES` 是 `label=id`：关闭 web 工具的自定义框架用其 `chrn_` id，内置框架用其后端名。`TASKS` 是 `first:N` 或 id 的逗号列表；默认是整个包。可续跑：某个框架 × 模型 × 包已记录的任务会跳过，带 `error`（运行器自身失败）的记录会重跑。会话评分后即删除，与矩阵一致，发现项的会话除外，保留以供读取其 trace；`KEEP=1` 全部保留。控制台代理把同步轮次截断在五分钟的实例（#214 之前）仍然运行了它：运行器找到它打开的会话，从记录评分。

## 第一列

SpreadsheetBench Verified 的五十个任务（`dataset.json` 的前五十个），四个关闭 web 工具的框架，`deepseek-v4.1-flash` 通过一个自定义 OpenAI 格式连接，在自托管 CE 上：pi 和 dsh 在 0.18.0（2026-09-18），cline 在 0.18.4（2026-09-19，含 #209），opencode 在 0.18.4 并应用了 #216（2026-09-19），这样每行的 token 都在同一口径上。两百次运行，两个 worker；生成的表格及其发现项见 [docs/benchmark.md](../../docs/benchmark.md)，记录见 [docs/benchmark-results.json](../../docs/benchmark-results.json)。两个任务通不过自己的评分器，被剔除；三次查答案和一次网络请求是发现项，不是分数。

| 框架 | 已解决 | 墙钟（总和） | 墙钟中位数 | 工具调用 | 失败调用 | 新输入 | 缓存输入 | 输出 |
|---|---|---|---|---|---|---|---|---|
| pi | 40/47 (85%) | 3605 s | 48 s | 526 | 89 (17%) | 484k | 7.53M | 546k |
| opencode | 39/48 (81%) | 5515 s | 75 s | 563 | 67 (12%) | 666k | 11.64M | 709k |
| dsh | 36/46 (78%) | 6506 s | 100 s | 721 | 113 (16%) | 761k | 12.32M | 752k |
| cline | 36/47 (77%) | 6882 s | 108 s | 736 | 121 (16%) | 1.20M | 19.74M | 1.21M |

在 48 个可评分任务中，31 个被四个框架全部解决，6 个无一解决；其余 11 个各有分歧，其中只有一个被单一框架解决（opencode，80-42）。pi 的七个失败就是那六个加上这一个，墙钟时间是其余的一半；另外三个多丢两到四个，大多各不相同。差距在成本上，同样的任务、同样的模型：pi 与 cline 之间新输入差 2.5×，缓存差 2.6×，输出 token 差 2.2×，墙钟时间差 1.9×。运行失败时大多是彻底失败：答案单元格错误（26 次）或未保存工作簿（11 次）；唯一触及时间上限的运行也是唯一访问了网络的。

规则 2 在 cline 或 dsh 上无法检查：通过自定义 OpenAI 格式连接，它们的轮次记录不带实际服务模型（opencode 带，pi 带）。实例的控制台代理仍把同步轮次截断在五分钟（#214 此后已合并）；20 次运行越过了它，从会话列表恢复并从记录评分。更早的两列被搁置：cline 在 #209 之前的 0.18.0（50 中 36，输入按毛值报告为 18.87M）和 opencode 在 #216 之前（48 中 37，输出报告为 81k 可见文本，而同样任务生成约 700k），后者正是发现该 bug 的原因——同一模型上两个框架之间 15× 的差距是记账问题。
